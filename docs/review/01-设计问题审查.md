# StreamMQ 设计问题审查报告

> 审查视角：以开源项目发布标准，全面否定性审查项目设计层面的问题
> 审查日期：2026-07-21
> 审查结论：**存在 12 项设计问题（4 项严重 / 5 项重要 / 3 项一般）**

---

## 一、严重问题（必须修复）

### 1.1 Message 类设计为可变对象，违反消息系统不可变性原则

**位置**：`streammq-core/.../message/Message.java`

**问题描述**：
`Message` 类使用 Lombok `@Data` 注解，所有字段均可通过 setter 修改。在消息系统中，消息一旦创建就应该是不可变的（immutable），以避免并发安全问题和消息篡改风险。

```java
@Data  // 生成所有 getter/setter，消息对象完全可变
public class Message<T> implements Serializable {
    private String topic;
    private String tag;
    private String keys;
    private String body;
    // ... 所有字段均可通过 setter 修改
}
```

**影响**：
- 消息在传递过程中可能被拦截器/过滤器意外修改
- 在并发消费场景下存在线程安全风险
- 违反 RocketMQ 的设计哲学（RocketMQ 的 Message 是可变的，但这是被广泛批评的设计缺陷）

**建议**：
- 使用 `@Value(Immutable)` 或手动构建不可变对象
- 提供 `MessageBuilder` 一次性构建，不提供 setter
- 如需修改属性，提供 `withXxx()` 返回新实例的方法

---

### 1.2 StreamMessageTemplate 接口方法签名过于复杂

**位置**：`streammq-core/.../template/StreamMessageTemplate.java`

**问题描述**：
接口定义了 3 个重载的 `syncSend` 方法，参数仅为 `timeoutMillis` 和 `retryTimes` 的区别：

```java
<T> SendResult syncSend(Message<T> message);
<T> SendResult syncSend(Message<T> message, long timeoutMillis);
<T> SendResult syncSend(Message<T> message, long timeoutMillis, int retryTimes);
```

这是典型的"参数爆炸"反模式。同样的问题存在于 `asyncSend`（3个重载）和 `sendOneway`（2个重载），总计 8 个方法中至少 5 个可以通过 Builder 模式合并。

**影响**：
- API 表面积过大，用户学习成本高
- 未来新增参数（如优先级、延迟策略）将导致更多重载
- 与 `DefaultStreamMessageService` 中 50+ 个方法形成恶性循环

**建议**：
- 引入 `SendOptions` 配置对象：`syncSend(Message<T>, SendOptions)`
- 保留 1-2 个便捷重载，其余通过 Builder 配置

---

### 1.3 ConsumerFilter SPI 缺乏实际实现

**位置**：`streammq-core/.../filter/` 下的 `TagSelectorFilter`、`SqlSelectorFilter`

**问题描述**：
这两个过滤器都是 **抽象类**，不是具体实现。项目中没有提供 `TagSelectorFilter` 和 `SqlSelectorFilter` 的具体子类实现（如 `DefaultTagSelectorFilter`）。

```java
public abstract class TagSelectorFilter implements ExpressionSelectorFilter {
    protected abstract boolean matchTag(String tag);  // 无具体实现
}
```

README 和文档中宣称支持 Tag 过滤和 SQL92 过滤，但实际没有可用的具体实现类。用户看到 `selectorExpression` 配置项后会认为可以直接使用，实际无法工作。

**影响**：
- **功能欺诈**：文档承诺的能力实际不可用
- 用户配置 `selectorExpression` 后不会有任何过滤效果
- SQL92 过滤作为卖点，实际连 SQL 解析器都没有

**建议**：
- 必须实现 `DefaultTagSelectorFilter`（解析 `tag1 || tag2` 表达式）
- SQL92 过滤需要引入 JSqlParser 或类似库实现，或至少在文档中标注为"实验性"

---

### 1.4 反射实例化 SPI 缺乏类型安全

**位置**：`streammq-spring-boot-starter/.../StreamMQCoreAutoConfiguration.java`

**问题描述**：
通过 `Class.forName(className).getDeclaredConstructor().newInstance()` 反射实例化 SPI 实现，仅在运行时检查类型兼容性：

```java
private static <T> T instantiate(String className, Class<T> expectedType) {
    Class<?> clazz = Class.forName(className, true, Thread.currentThread().getContextClassLoader());
    if (!expectedType.isAssignableFrom(clazz)) {
        throw new IllegalArgumentException(...);
    }
    return (T) clazz.getDeclaredConstructor().newInstance();
}
```

**影响**：
- 类名拼写错误只在运行时发现，无法在编译期/启动期检测
- 无参构造函数要求未文档化，用户自定义 SPI 可能因缺少无参构造而失败
- 反射实例化的 Bean 无法被 Spring 容器管理，无法注入其他依赖

**建议**：
- 使用 Spring Boot 的 `SpringFactoriesLoader` 或 `@AutoService` 模式
- 至少在启动时（`@PostConstruct`）预校验所有配置的类名是否可加载

## 二、重要问题（应该修复）

### 2.1 广播消费模式（BROADCASTING）设计不完整

**位置**：`streammq-core/.../enums/ConsumeMode.java` 及 `DefaultStreamMQListenerContainer`

**问题描述**：
`ConsumeMode.BROADCASTING` 在枚举和注解中定义，但 `DefaultStreamMQListenerContainer` 的实现中，广播消费的消费者组命名逻辑不清晰。广播模式下每个消费者实例应有独立的 consumer group，但当前实现未明确如何生成唯一组名。

```java
// ConsumeMode.java 只有枚举定义
public enum ConsumeMode {
    CLUSTERING,
    BROADCASTING
}
```

**影响**：
- 广播消费在多实例部署时可能出现消息重复或丢失
- 用户无法可靠使用广播消费模式

---

### 2.2 TransactionScanner 单点故障风险

**位置**：`streammq-redisson/.../scheduler/TransactionScanner.java`

**问题描述**：
事务回查调度器在单节点模式下运行，如果该节点宕机，事务回查将完全停止，导致半消息永远处于"未知"状态。

```java
public class TransactionScanner implements StreamMQScheduler {
    // 单线程调度，无故障转移
    private final ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor(...);
}
```

**影响**：
- 生产环境中事务消息的可靠性无法保证
- 半消息可能永久悬挂，既不提交也不回滚

**建议**：
- 基于 Redis 的分布式锁实现 leader election
- 多实例部署时只有一个节点执行扫描

---

### 2.3 DLQ 二级队列设计缺乏回流机制

**位置**：`streammq-core/.../policy/DlqConfig.java`、`DlqFailureStrategy.java`

**问题描述**：
二级死信队列（`secondaryDlqEnabled`）只定义了从一级 DLQ 转入二级 DLQ 的路径，但没有定义：
- 二级 DLQ 消息如何被消费
- 二级 DLQ 消息如何重新投递到主队列（回流）
- 二级 DLQ 的消费者注册方式

```java
@Builder.Default
private boolean secondaryDlqEnabled = false;
@Builder.Default
private String secondaryDlqKeyPrefix = "dlq2";
```

**影响**：
- 二级 DLQ 只是一个存储桶，无法被消费和处理
- 消息进入二级 DLQ 后基本等于丢失

---

### 2.4 缺乏消息轨迹的持久化存储

**位置**：`streammq-tracing/` 模块

**问题描述**：
链路追踪模块（`streammq-tracing`）将追踪数据写入内存或 SLF4J 日志，没有持久化存储方案。`MessageTrace` 对象仅存在于 `StreamMQTopologyService` 的内存 Map 中。

```java
public class StreamMQTopologyService {
    private final Map<String, MessageTrace> traceStore = new ConcurrentHashMap<>();
}
```

**影响**：
- 服务重启后追踪数据全部丢失
- 无法进行历史消息的链路回溯
- 在生产环境中几乎无实用价值

---

### 2.5 K8s 模块与 Spring Boot Starter 职责重叠

**位置**：`streammq-cloud-k8s/` 与 `streammq-spring-boot-starter/`

**问题描述**：
两个模块都提供了健康检查端点（`StreamMQHealthIndicator`），都实现了 `HealthIndicator` 接口。K8s 模块的 `StreamMQHealthController` 提供 REST 端点，而 Starter 模块通过 Actuator 暴露健康信息。

**影响**：
- 同时引入两个模块会导致 `HealthIndicator` Bean 冲突
- 用户不清楚应该使用哪个模块的健康检查
- 运维端点路径不统一（`/actuator/streammq` vs `/streammq/health`）

---

## 三、一般问题（建议修复）

### 3.1 MessageBuilder 的冗余方法命名

**位置**：`streammq-core/.../message/MessageBuilder.java`

**问题描述**：
Builder 同时提供带 `with` 前缀和不带前缀的方法：

```java
public MessageBuilder<T> withTopic(String topic) { ... }
public MessageBuilder<T> topic(String topic) { ... }  // 重复
public MessageBuilder<T> withTag(String tag) { ... }
public MessageBuilder<T> tag(String tag) { ... }  // 重复
```

**影响**：
- API 表面积翻倍
- 用户困惑应该用哪种风格
- 文档示例中两种风格混用，增加学习成本

---

### 3.2 ConsumeAction 的 defer 机制设计模糊

**位置**：`streammq-core/.../enums/ConsumeAction.java`

**问题描述**：
`ConsumeAction.defer(Duration)` 提供了自定义延迟重试能力，但文档中未说明：
- defer 的消息是否进入重试队列
- defer 与 `RECONSUME_LATER` 的区别是什么
- defer 的 Duration 上限是多少

---

### 3.3 StreamMessageService 接口继承层次过深

**位置**：`streammq-core/.../service/StreamMessageService.java`

**问题描述**：
`StreamMessageService` 继承了 6 个子接口：

```java
public interface StreamMessageService extends
    BasicMessageService,
    AsyncMessageService,
    OnewayMessageService,
    BatchMessageService,
    DelayMessageService,
    TransactionMessageService { }
```

虽然这是接口隔离原则（ISP）的正确应用，但 `DefaultStreamMessageService` 实现了所有 50+ 个方法，且很多方法签名仅差一个参数。对于开源项目，用户面对 50+ 个方法会感到困惑。
