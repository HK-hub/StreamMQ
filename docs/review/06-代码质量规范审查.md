# StreamMQ 代码质量规范审查报告

> 审查视角：以开源项目发布标准，全面否定性审查项目代码质量和规范问题
> 审查日期：2026-07-21
> 审查结论：**发现 14 项代码质量问题（4 项严重 / 6 项重要 / 4 项一般）**

---

## 一、严重问题（必须修复）

### 1.1 大量 `@SuppressWarnings("unchecked")` 掩盖类型安全问题

**位置**：多处，特别是 `StreamMQListenerRegistrar.java`、`DefaultStreamMessageTemplate.java`

**问题描述**：
项目中频繁使用泛型压制注解来规避类型检查：

```java
// StreamMQListenerRegistrar.java
@SuppressWarnings({"unchecked", "rawtypes"})
private void registerStreamMQListeners() {
    Map<String, Object> beans = applicationContext.getBeansWithAnnotation(StreamMQConsumer.class);
    for (Map.Entry<String, Object> entry : beans.entrySet()) {
        Object bean = entry.getValue();
        // 强制类型转换，无运行时检查
        StreamMessageConcurrentlyConsumer listener = (StreamMessageConcurrentlyConsumer) bean;
    }
}
```

**影响**：
- 如果用户实现的 Consumer 类型不匹配（如 `StreamMessageConcurrentlyConsumer<Integer>` 而消息是 `String`），在消费时才会抛出 `ClassCastException`
- 编译期完全无法捕获类型不匹配错误

**建议**：
- 使用 `TypeToken` 或 `ParameterizedTypeReference` 在运行时获取泛型参数
- 在注册时校验 Consumer 的泛型参数与消息类型是否兼容

### 1.2 硬编码的魔法值散布在代码中

**位置**：多处

**问题描述**：
```java
// DefaultStreamMQListenerContainer.java
private static final int DEFAULT_PULL_BATCH_SIZE = 32;
private static final long DEFAULT_CONSUME_TIMEOUT = 30_000L;
private static final int DEFAULT_INFLIGHT_CAPACITY = 1000;
// ... 这些值应该在 StreamMQConstants 中统一定义

// StreamMQHealthAutoConfiguration.java
private static final String HEALTH_CHECK_KEY = "streammq:health-check";
// 未使用 StreamMQKeys 中的常量

// TransactionScanner.java
private static final int SCAN_BATCH_SIZE = 100;
// 与配置中的 batch-size 不一致
```

**影响**：
- 相同含义的值在不同位置有不同的定义
- 修改一个值需要搜索整个代码库
- 用户配置的值可能被代码中的硬编码值覆盖

---

### 1.3 异常处理策略不统一

**位置**：多处

**问题描述**：
项目中至少使用了 5 种不同的异常处理策略，且没有统一的异常体系：

```java
// 策略1：抛出运行时异常
throw new StreamMQException("Failed to send message", ex);

// 策略2：记录日志并返回 null
LOG.error("Failed to...", ex);
return null;

// 策略3：记录日志并吞没异常
LOG.warn("...", ex);
// 继续执行

// 策略4：包装为 IllegalArgumentException
throw new IllegalArgumentException("Class " + className + "...", ex);

// 策略5：抛出 IllegalStateException
throw new IllegalStateException("Already started", ex);
```

**影响**：
- 调用方无法确定应该捕获哪种异常
- null 返回值导致 NullPointerException 风险
- 异常信息不统一，难以在日志中进行有效的错误分类

**建议**：
- 定义统一的异常层次：`StreamMQException`（基础）→ `SendException`/`ConsumeException`/`ConfigException`
- 所有公开方法使用 checked exception 或明确声明使用 unchecked exception
- 移除所有返回 null 的异常处理路径

---

### 1.4 缺乏 Null Safety 的一致策略

**问题描述**：
项目中对 null 的处理策略混乱：

```java
// 有些地方使用 @NonNull 注解
@NonNull
private final String topic;

// 有些地方使用 Objects.requireNonNull
Objects.requireNonNull(message, "message");

// 有些地方不检查 null
public void setFilterResolver(FilterResolver filterResolver) {
    this.filterResolver = filterResolver;  // 不检查 null
}

// 有些地方返回 null
public Message<?> getMessage() {
    return this.message;  // 可能为 null
}
```

**影响**：
- NPE 成为最常见的运行时异常
- 用户使用 API 时不确定哪些参数可以为 null

## 二、重要问题（应该修复）

### 2.1 Javadoc 覆盖率不均匀

**问题描述**：
- **Core 模块**：Javadoc 覆盖率高，所有公开接口和方法都有完整的中文 Javadoc
- **Redisson 模块**：Javadoc 覆盖率中等，部分实现类缺少 Javadoc
- **Starter 模块**：Javadoc 覆盖率高（与 Core 模块一致）
- **Tracing/Diagnostics/K8s 模块**：Javadoc 覆盖率低，很多类和方法缺少 Javadoc

具体问题：
```java
// streammq-tracing 中的类缺少 Javadoc
public class StreamMQTracingAutoConfiguration {
    // 无类级 Javadoc
    // 无方法级 Javadoc
}
```

---

### 2.2 日志级别使用不当

**问题描述**：
```java
// 不应该用 INFO 级别输出配置信息（启动时输出一次即可）
LOG.info("Using DefaultMessageConverter with serializer={}", serializer.getClass().getSimpleName());
LOG.info("Creating DefaultStreamMessageTemplate: defaultGroup={}, ...", defaultGroup, txGroup, namespace);
LOG.info("Creating StreamMQHealthIndicator");
// ... 大量 INFO 级别的 Bean 创建日志

// 不应该用 WARN 级别输出正常的业务逻辑
LOG.warn("No RedissonClient bean found, creating default localhost:6379 instance...");
```

**影响**：
- 启动时日志被大量无用的 Bean 创建信息淹没
- 真正的 WARN 和 ERROR 信息被淹没在 INFO 日志中
- 用户无法快速定位问题

**建议**：
- Bean 创建日志改为 DEBUG 级别
- 仅在异常配置时输出 WARN
- 添加 `@ConfigurationProperties` 的校验错误输出

---

### 2.3 测试代码质量参差不齐

**问题描述**：
- **单元测试**：覆盖了核心功能，但有些测试过于简单（仅验证方法不抛异常）
- **集成测试**：依赖 Testcontainers，但没有验证异常场景
- **缺少的测试**：
  - 并发安全测试
  - 性能基准测试
  - 故障注入测试（Redis 断连、超时等）
  - 消息大小边界测试
  - 序列化兼容性测试

```java
// 典型的"烟雾测试"——只验证不抛异常
@Test
void testSend() {
    SendResult result = template.syncSend(message);
    assertThat(result).isNotNull();
}
// 没有验证 result 的内容、没有验证消息是否到达消费者
```

---

### 2.4 依赖版本管理存在风险

**位置**：根 `pom.xml`

**问题描述**：
```xml
<!-- 使用 SNAPSHOT 版本 -->
<version>0.1.0-SNAPSHOT</version>

<!-- 依赖版本可能过时 -->
<spring-boot.version>3.3.5</spring-boot.version>  <!-- 最新可能是 3.4.x -->
<redisson.version>3.34.1</redisson.version>  <!-- 需要检查是否为最新稳定版
```

**风险**：
- SNAPSHOT 版本不适合发布到 Maven Central
- 依赖版本可能包含已知漏洞（CVE）
- 没有 Dependabot 或类似工具自动更新依赖

---

### 2.5 代码注释使用中文但不完全一致

**问题描述**：
项目中的代码注释使用中文，但风格不统一：

```java
// 有些注释详细完整
/**
 * StreamMQ 消息转换器 SPI，负责将业务对象转换为消息体字节流，或反向转换。
 * <p>核心职责：
 * <ul>
 *   <li>序列化：将 {@code <T> body} 编码为 {@code byte[]}（写入 Redis 前）</li>
 *   <li>反序列化：将 {@code byte[]} 解码为 {@code <T> body}（从 Redis 读取后）</li>
 * </ul>
 */

// 有些注释过于简略
// 默认构造
public RedissonStreamProducerFactory() {}

// 有些注释是无用的重复
// 获取 topic
public String getTopic() { return topic; }
```

### 2.6 缺乏代码格式化的强制执行

## 三、一般问题（建议修复）

### 3.1 Package 结构不够清晰

**问题描述**：
`streammq-redisson` 模块的包结构：

```
io.github.streammq.adapter.redisson
├── compression/    # 压缩
├── container/      # 容器
├── converter/      # 转换器
├── dlq/           # 死信队列
├── filter/        # 过滤器
├── handler/       # 处理器
├── interceptor/   # 拦截器
├── listener/      # 监听器
├── lock/          # 锁
├── manager/       # 管理器
├── metrics/       # 指标
├── producer/      # 生产者
├── rebalance/     # 重平衡
├── retry/         # 重试
├── scheduler/     # 调度器
├── security/      # 安全
├── serializer/    # 序列化器
├── support/       # 支持工具
├── template/      # 模板
└── trace/         # 追踪
```

包数量过多（20+），且部分包只有一个类（如 `lock/`、`manager/`），增加了导航复杂度。

---

### 3.2 Lombok 使用过度

**问题描述**：
项目大量使用 Lombok，虽然减少了样板代码，但：
1. 增加了 IDE 配置要求（需要安装 Lombok 插件）
2. 调试时无法直接看到 getter/setter 的实现
3. 在 Javadoc 生成时需要额外配置
4. 对于开源项目，贡献者需要理解 Lombok 注解的语义

---

### 3.3 缺乏代码复杂度控制

**问题描述**：
`DefaultStreamMQListenerContainer` 有 1039 行代码，`DefaultStreamMessageTemplate` 有 641 行代码。这些核心类过于庞大，包含了大量的条件分支和嵌套逻辑。

**建议**：
- 单个类不应超过 500 行
- 核心方法不应超过 50 行
- 使用 Extract Method / Extract Class 重构

---

### 3.4 缺乏 API 兼容性保证

**问题描述**：
项目没有声明 API 兼容性策略。对于开源项目，用户期望：
- Minor 版本升级不会破坏现有 API
- Deprecated API 会保留至少一个 Minor 版本
- 重大变更会在 CHANGELOG 中明确说明

当前 `0.1.0-SNAPSHOT` 版本没有 CHANGELOG 文件。
