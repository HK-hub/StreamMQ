# StreamMQ 功能规划问题审查报告

> 审查视角：以开源项目发布标准，全面否定性审查项目功能规划的问题
> 审查日期：2026-07-21
> 审查结论：**存在 10 项功能规划问题（3 项严重 / 4 项重要 / 3 项一般）**

---

## 一、严重问题（必须修复）

### 1.1 功能承诺与实际实现严重脱节

**问题描述**：
README 中宣称的多项核心功能在代码中没有完整实现或完全没有实现：

| 功能 | README 承诺 | 实际状态 |
|------|------------|---------|
| SQL92 消息过滤 | ✅ "支持 SQL92 表达式过滤" | ❌ `SqlSelectorFilter` 是抽象类，无具体实现 |
| Tag 消息过滤 | ✅ "支持 Tag 表达式过滤" | ⚠️ `TagSelectorFilter` 是抽象类，无具体实现 |
| 广播消费 | ✅ "支持广播消费" | ⚠️ 枚举定义了但实现不完整 |
| 消息压缩 | ✅ "支持 GZIP/LZ4/Snappy" | ⚠️ 仅实现 GZIP，LZ4 和 Snappy 只是占位 |
| 二级死信队列 | ✅ "含二级 DLQ" | ⚠️ 配置项存在但消费路径未实现 |
| 链路追踪 | ✅ "支持 OpenTelemetry" | ⚠️ `streammq-tracing` 模块存在但仅输出 SLF4J 日志 |

**影响**：
- 用户按文档配置后发现功能不工作，严重损害项目信誉
- 在 X/YouTube 推广后收到负面反馈的风险极高
- 可能被 GitHub 社区标记为"vaporware"

**建议**：
- 发布前必须逐项验证 README 中承诺的每一项功能
- 未完成的功能标注为 `@Experimental` 或从 v1.0 中移除
- 建立功能矩阵，每个功能标注"已实现/实验性/计划中"

---

### 1.2 Spring Cloud Stream Binder 功能不完整

**位置**：`streammq-spring-cloud-stream-binder/` 模块

**问题描述**：
该模块存在于代码库中并被包含在 v1.0 路线图中，但实际上：

1. **模块在 README 中未提及**：模块结构表中没有列出此模块
2. **Binder 的消息可靠性未验证**：`StreamMQMessageHandler` 中的消息发送缺少重试和确认机制
3. **Binder 缺乏与 Spring Cloud 生态的集成测试**：没有与 Spring Cloud Config、Spring Cloud Bus 等的集成测试
4. **消费者绑定配置不完整**：`StreamMQConsumerProperties` 中的字段与 `@StreamMQConsumer` 注解的属性不完全对应

**影响**：
- Spring Cloud 用户期望 Binder 能直接替换 Kafka/RabbitMQ Binder，但当前实现无法满足
- 作为 v1.0 功能发布会被社区质疑

---

### 1.3 Kubernetes Operator 功能未实现但模块已存在

**位置**：`streammq-cloud-k8s/` 模块

**问题描述**：
v1.0 路线图声称支持 K8s，但实际只提供了：
- 健康检查端点（与 Starter 模块重复）
- 优雅停机处理器
- HPA 指标提供者
- 配置热更新（仅定义了接口，无实际实现）

缺失的关键功能：
- **CRD 定义**：没有 Kubernetes CustomResourceDefinition
- **Operator 控制器**：没有 Operator 逻辑
- **自动扩缩容**：HPA 只是暴露指标，没有自动扩缩容逻辑
- **配置热更新**：`StreamMQConfigRefresher` 接口只有一个 `NoopConfigRefresher` 实现

**影响**：
- 模块的存在给用户造成"K8s 已完全支持"的错误印象
- 实际上只是一个健康检查 + 指标暴露的工具包

## 二、重要问题（应该修复）

### 2.1 v2.0 路线图过于激进，稀释 v1.0 价值

**问题描述**：
v1.0 路线图和 v2.0 规划文档同时存在于项目中，v2.0 计划了：
- 多后端抽象层（Kafka/RabbitMQ/Pulsar）
- 跨机房复制
- Kafka 线网协议兼容
- Kubernetes Operator
- 消息画像与拓扑图

这些功能在 v1.0 尚未稳定的情况下规划，给用户传递了"这个项目还没准备好"的信号。

**影响**：
- 用户不敢在生产环境使用 v1.0，因为不确定是否会很快被 v2.0 替代
- 功能范围过大导致 v1.0 质量无法保证

**建议**：
- v2.0 规划文档移至 `docs/future/` 或标注为"实验性规划"
- v1.0 README 中只展示 v1.0 已实现的功能

---

### 2.2 消息体大小限制未定义

**问题描述**：
Redis Stream 的单个消息最大大小为 512MB，但项目中没有：
- 消息体大小校验
- 超大消息的拒绝策略
- 消息体大小的监控指标
- 文档中未说明消息大小限制

```java
// MessageBuilder 中无大小校验
public MessageBuilder<T> body(T body) {
    this.body = body;
    return this;
}
```

**影响**：
- 用户可能发送超大消息导致 Redis 内存耗尽
- 序列化后的消息大小不可预测（特别是 JSON 序列化嵌套对象时）

---

### 2.3 消费者 rebalance 策略缺乏文档和测试

**问题描述**：
项目提供了两种 rebalance 策略：
- `AverageRebalanceStrategy` - 平均分配
- `ConsistentHashRebalanceStrategy` - 一致性哈希

但：
1. 两种策略的行为差异未在文档中说明
2. 一致性哈希策略在消费者数量变化时的行为未文档化
3. rebalance 过程中的消息处理（是否暂停消费）未说明
4. 测试覆盖不足，仅有基础单元测试

---

### 2.4 消息过滤在 Broker 端 vs Client 端未明确

**问题描述**：
Tag/SQL92 过滤应该在 Redis Stream 层面（Broker 端）实现以减少网络传输，还是在客户端实现？

当前设计中：
- `SelectorExpression` 在注解中定义
- `ConsumerFilter` 在客户端执行
- 没有利用 Redis Stream 的 `XRANGE` 过滤能力

**影响**：
- 所有消息都会被拉取到客户端，仅在客户端过滤
- 在消息量大时浪费大量网络带宽

**建议**：
- 明确声明"过滤在客户端执行"
- 考虑利用 Redis 7.0+ 的 Stream 消费者组过滤能力（如果有）

---

## 三、一般问题（建议修复）

### 3.1 示例工程缺乏可运行性验证

**问题描述**：
`streammq-samples` 包含 6 个示例项目，但：
1. 没有 `docker-compose.yml` 提供本地 Redis 环境
2. 示例依赖 SNAPSHOT 版本，用户无法直接运行
3. 没有 README 说明如何运行示例
4. 示例代码未验证是否能通过编译

---

### 3.2 消息延迟级别硬编码

**位置**：`streammq-core/.../enums/DelayLevel.java`

**问题描述**：
18 级延迟完全硬编码在枚举中：

```java
public enum DelayLevel {
    SECOND_1(1000),
    SECOND_5(5000),
    // ... 18 级
}
```

用户无法自定义延迟级别，无法添加如 `HOUR_4`、`DAY_1` 等级别。

---

### 3.3 缺乏消息优先级支持

**问题描述**：
消息系统中常见的优先级队列能力未在功能规划中体现。对于订单系统等场景，高优先级消息（如支付回调）需要优先于低优先级消息（如通知推送）被消费。
