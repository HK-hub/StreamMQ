# StreamMQ 架构设计问题审查报告

> 审查视角：以开源项目发布标准，全面否定性审查项目架构设计的问题
> 审查日期：2026-07-21
> 审查结论：**发现 11 项架构问题（3 项严重 / 5 项重要 / 3 项一般）**

---

## 一、严重问题（必须修复）

### 1.1 模块依赖方向违反分层原则

**问题描述**：
项目的模块分层设计存在依赖方向混乱：

```
streammq-core（纯接口层）
    ↑
streammq-redisson（Redisson 适配层）← 依赖 core
    ↑
streammq-spring-boot-starter（Spring Boot 集成层）← 依赖 redisson + core
```

但在实际代码中：

1. **`StreamMQCoreAutoConfiguration` 直接引用了 redisson 模块的具体类**：

```java
import io.github.streammq.adapter.redisson.converter.DefaultMessageConverter;
import io.github.streammq.adapter.redisson.producer.RedissonStreamProducerFactory;
import io.github.streammq.adapter.redisson.template.DefaultStreamMessageTemplate;
// ... 直接引用适配层实现类
```

2. **Spring Boot Starter 同时依赖 core 和 redisson**，没有做到"只依赖接口"

**违反原则**：
- 分层架构中上层不应直接依赖下层的具体实现
- Starter 应该只依赖 core 的接口，通过 SPI 机制发现 redisson 的实现

**影响**：
- 无法替换 Redisson 为其他 Redis 客户端（如 Lettuce）
- 模块耦合度过高，违反开闭原则

**修复建议**：
- 引入 SPI 发现机制（`META-INF/services/` 或 Spring Boot 的 `@AutoService`）
- Starter 通过接口类型注入，不直接引用适配层类

---

### 1.2 Spring Boot Starter 与 Core 模块的职责边界模糊

**问题描述**：
`streammq-core` 声称"无 Spring 依赖"，但核心接口（如 `StreamMQListenerContainer`）的设计明显面向 Spring 生命周期：

```java
// core 模块中的接口 - 看似无 Spring 依赖
public interface StreamMQListenerContainer {
    void start();
    void stop();
    boolean isRunning();
}
```

而 `SmartLifecycle` 的适配在 Starter 模块中完成，但 `start()`/`stop()`/`isRunning()` 的语义与 Spring 的 `Lifecycle` 完全一致。

同时，`streammq-core` 中的一些类（如 `StreamMQConstants`）使用了 Spring 风格的命名（如 `DEFAULT_*` 常量），这在纯 Java 库中不常见。

**影响**：
- 如果用户不使用 Spring Boot，`core` 模块的接口无法直接使用（缺少生命周期管理）
- "无 Spring 依赖"的声明不完全准确

---

### 1.3 缺乏统一的消息可靠性保证模型

**问题描述**：
项目中多种消息发送模式的可靠性保证不一致，且未明确定义：

| 发送模式 | 可靠性保证 | 未明确的问题 |
|---------|-----------|-------------|
| syncSend | 未知 | 是否等待 Redis XADD 确认？ |
| asyncSend | 未知 | 异步 Future 何时 complete？ |
| sendOneway | 未知 | 是否 fire-and-forget？ |
| sendBatch | 未知 | Pipeline 中单条失败如何处理？ |
| executeInTransaction | 部分 | 简化模式无持久化保证 |

**核心问题**：
Redis Stream 的 `XADD` 命令在默认配置下是异步写入的（`appendfsync everysec`），即使 `XADD` 返回成功，消息也可能在 Redis 崩溃时丢失。

项目中没有：
- 明确声明每种发送模式的持久化级别
- 提供 `XADD` 的 `NOMKSTREAM` 选项配置
- 提供 Redis `WAIT` 命令的集成（等待主从同步确认）

**影响**：
- 用户无法根据业务可靠性需求选择正确的发送模式
- 在金融等高可靠性场景下可能造成数据丢失

## 二、重要问题（应该修复）

### 2.1 Listener Container 的线程模型不清晰

**位置**：`streammq-redisson/.../container/DefaultStreamMQListenerContainer.java`

**问题描述**：
`DefaultStreamMQListenerContainer` 使用 Java 21 的虚拟线程（Virtual Threads）作为消费线程：

```java
private final ExecutorService consumeExecutor = Executors.newVirtualThreadPerTaskExecutor();
```

但线程模型存在以下不清晰之处：
1. 虚拟线程的数量不受 `consumeThreadMin`/`consumeThreadMax` 控制（虚拟线程是无限创建的）
2. 背压队列（InflightQueue）的大小与线程数的关系未说明
3. 在虚拟线程中执行 Redis I/O 操作时，`synchronized` 块是否会 pin carrier thread

**影响**：
- 用户配置的 `consumeThreadMin`/`consumeThreadMax` 可能被忽略
- 虚拟线程的使用可能导致难以调试的性能问题

---

### 2.2 SPI 发现机制与 Spring Bean 注册机制并存

**问题描述**：
项目同时使用了两种扩展机制：
1. **Java SPI**（`META-INF/services/`）用于 core 模块的 SPI 接口
2. **Spring Bean**（`@ConditionalOnMissingBean`）用于 Starter 模块的 Bean 注册

这导致：
- 在非 Spring 环境中，SPI 可能无法正常工作（缺少 `META-INF/services/` 文件）
- 在 Spring 环境中，SPI 和 Bean 注册可能产生冲突
- 用户不清楚应该用哪种方式扩展

---

### 2.3 缺乏消息 Schema 演进策略

**问题描述**：
项目使用 Jackson JSON 序列化消息体，但没有定义消息 Schema 演进策略：
- 当生产者修改了消息体结构（新增字段、删除字段）时，消费者如何兼容？
- 是否应该支持消息版本号？
- 是否应该支持 Schema Registry？

**影响**：
- 在微服务架构中，服务独立部署时消息格式变更会导致反序列化失败
- 缺乏前向/后向兼容性保证

---

### 2.4 缺乏资源泄漏检测机制

**问题描述**：
项目中使用了大量的异步资源（`ScheduledExecutorService`、`ExecutorService`、`RStream`、`RBucket` 等），但缺乏统一的资源泄漏检测：

1. 没有实现 `Closeable`/`AutoCloseable` 接口（除了 ListenerFactory）
2. 没有资源注册表（Registry）跟踪所有分配的资源
3. 在异常路径下资源可能未被正确释放
4. 没有提供 `leakDetection` 配置选项

---

### 2.5 健康检查端点缺乏深度检查

**位置**：`streammq-spring-boot-starter/.../StreamMQHealthAutoConfiguration.java`

**问题描述**：
当前健康检查仅验证 Redis 连通性和 Listener 容器状态，但缺少：
- Consumer Group 的 PENDING 消息数量检查
- 消费者线程池的活跃线程数检查
- 延时队列（ZSet）的堆积量检查
- 事务回查调度器的运行状态检查
- 序列化器/反序列化器的可用性检查

## 三、一般问题（建议修复）

### 3.1 模块命名不符合 Maven 约定

**问题描述**：
项目中的模块命名使用了 `streammq-` 前缀，但子模块命名风格不统一：

| 模块名 | 问题 |
|--------|------|
| `streammq-bom` | OK |
| `streammq-core` | OK |
| `streammq-redisson` | 应为 `streammq-adapter-redisson`（明确是适配层） |
| `streammq-spring-boot-starter` | OK |
| `streammq-tracing` | 应为 `streammq-tracing-opentelemetry`（明确追踪实现） |
| `streammq-diagnostics` | OK |
| `streammq-cloud-k8s` | 应为 `streammq-kubernetes`（更标准的命名） |
| `streammq-spring-cloud-stream-binder` | OK |
| `streammq-test` | OK |
| `streammq-samples` | OK |

---

### 3.2 配置属性缺乏嵌套校验

**问题描述**：
`StreamMQProperties` 使用了多层嵌套配置，但没有使用 Spring Boot 的 `@Validated` 进行嵌套校验：

```java
@Data
@ConfigurationProperties(prefix = "streammq")
public class StreamMQProperties {
    private Producer producer = new Producer();
    // 没有 @Validated 注解
    // 没有嵌套校验
    
    @Data
    public static class Producer {
        private int sendTimeout = 3000;
        // sendTimeout < 0 时不会报错
    }
}
```

---

### 3.3 模块间通信缺乏事件机制

**问题描述**：
各模块之间的通信完全通过直接依赖和方法调用，缺乏事件驱动的解耦机制。例如：
- 消息发送成功后，Tracing 模块需要记录轨迹
- 消息消费失败后，Diagnostics 模块需要记录失败信息

当前实现是在各处直接注入 `TraceCollector`、`StreamMQMetrics` 等接口，导致核心模块需要知道所有扩展模块的存在。

## 五、架构改进建议

### 5.1 短期（v1.0 发布前）

1. 明确每种发送模式的可靠性保证，在 Javadoc 和文档中声明
2. 修复模块依赖方向，至少在文档中声明"Starter 与 Redisson 实现紧耦合"
3. 为虚拟线程模型添加文档说明，解释 `consumeThreadMin/Max` 的实际效果

### 5.2 中期（v1.1-v1.2）

1. 引入消息版本号机制
2. 引入事件驱动机制解耦模块间通信
3. 增强健康检查的深度

### 5.3 长期（v2.0）

1. 实现 SPI 发现机制替代直接依赖
2. 引入 BackendProvider 抽象层
3. 支持多 Redis 客户端实现（Lettuce/Jedis/Redisson 可切换）
